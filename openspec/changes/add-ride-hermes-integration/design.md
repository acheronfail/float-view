# Design

## Reference implementation

Ride Hermes confirmed through Mark that Float Control is the integration to follow. The inspected Float Control Android APK was `com.floatcontrol` 3.6.8 (306081), with the Hermes client in `classes4.dex`. Its sign-in and ride submission code establish the following baseline for Float View.

| Operation | Observed behavior |
| --- | --- |
| Sign in | `POST /api/developer/v0/auth` with top-level `email` and `password`. The response contains `auth_token` and a user with ID, username, and email fields. |
| Partner and rider identity | Requests use `organization` and `api_key` headers, with separate keys for authentication and uploads. Ride submission also sends `auth_token`. |
| Submit a ride | `POST /api/developer/v0/rides` with top-level `title`, `desc`, `polyline`, `distance`, `elapsed_time`, `start_time`, `end_time`, `user_vehicle_id`, and `locations_attributes`. The inspected upload call leaves the vehicle ID unset. |
| Route encoding | The polyline uses latitude/longitude deltas at five decimal places. Ride and point timestamps use UTC with second precision. Each location has `lat`, `lng`, `timestamp`, `speed`, `altitude`, and `accuracy`. Float Control sends VESC speed in mph, passes through GPS altitude and horizontal accuracy, and substitutes zero for missing altitude or accuracy. |
| Receipt | The client reads `ride.id` from the response and records it locally. |

The comparison below also uses Floaty 3.0.0 (379) and its older fork at commit `c4c87fe`. The APK checks cover the shipped upload path, and the fork shows the capture and conversion code. Decompilation shows what each client sends and how it handles responses. Server acceptance and processing still need a test account.

## Account and credentials

- Start sign-in from Settings. Use a native credential prompt initiated through the mandatory backend contract. Hand email and password to the process-owned Rust service through the existing native boundary for a single HTTPS authentication request. Keep password fields and token material out of the WebView, loopback messages, diagnostics, and portable data. Clear transient credentials when the attempt finishes or is canceled.
- Store the resulting rider token using the host's protected credential store. Use the stable Hermes user ID to bind receipts and upload attempts to the account. Expose only bounded display identity and operation status. Disconnect clears the saved credential, cancels unsent work, and prevents a late sign-in or upload response from updating a replacement account's state.
- Use Float View's partner organization and separate keys for sign-in and ride uploads. If the partner credential is approved for distribution in a public app, the Rust service can call Hermes directly. If Hermes requires a confidential credential, resolve the server-side exchange and deployment before enabling the integration. Placeholder credentials return the same contract with unavailable status. Native adapters use a fixed Hermes HTTPS origin and decline redirects.

## Ride preparation

- Prepare one stable, completed session revision through the existing bounded readers. Use accepted location points in recorded order with their observed timestamps. Generate the polyline from the same coordinates used in `locations_attributes`. Retain recorded gaps in the source and avoid synthetic points. Encode one polyline across retained points, as in both reference clients. Preserve recorded gaps locally and actual sample timing in the payload.
- Join each location to the nearest eligible exact board-speed sample on the session's monotonic elapsed clock. Break equal-distance ties by lower sample sequence. Require a match within one second without crossing a recorded route gap. Never turn missing or stale telemetry into a measured zero. Convert saved km/h to mph at the Hermes boundary, independent of the rider's display units.
- Use nullable recorded GPS altitude in metres above the WGS84 ellipsoid and horizontal accuracy in metres. Existing sessions remain readable, including sessions without altitude. Apply Float Control’s zero fallback to missing altitude and accuracy at the wire boundary. Skip a point if no fresh board-speed sample exists.
- Use saved board distance in metres and elapsed seconds between the first and last included points. Require three points, 60 elapsed seconds, and 100 metres. Read at most 2,000 stored location points and 200,000 exact board samples, and cap the request at 384 KiB. Use a null vehicle ID.
- Prepare against the current linked account and revision. Confirm explicitly after showing the destination, that this submits the recorded GPS route, and which measurements will be shared. If the account or revision changes, invalidate the confirmation. CSV GPS preferences remain scoped to CSV.

## Upload lifecycle

- Serialize attempts by account and stable local recording identity. Save the attempt before sending and persist the remote ride ID before reporting success. Restore pending or confirmed outcomes after a restart. Keep upload receipts in a bounded SQLite database beside the recording root and outside portable archives. Store only account ID, local session ID, result status, and a confirmed remote ID. Follow the project's supported storage rules if catalog changes are needed.
- Use a partner-supported idempotency key or reconciliation path if available. If a request might have succeeded and Hermes offers neither, retain the uncertain outcome and prompt the rider to check their Hermes ride history before explicitly retrying. Treat a successful HTTP response with no usable receipt as uncertain. Keep confirmed receipts separate from trail or leaderboard processing status.
- Keep the WebView contract small. Put account and available actions in authoritative state. Return bounded per-session eligibility and result data via the authenticated contract. Maintain equivalent semantics in real hosts and the browser mock.

## Client behavior and decisions

| Question | Float Control 3.6.8 | Floaty 3.0.0 and older fork | Decision for Float View |
| --- | --- | --- | --- |
| What goes in speed, and what if it is missing? | Uses saved VESC speed from the same sample as the fix. Converts m/s to mph, keeps the sign, and rounds magnitudes below 0.001 mph to zero. | The fork drops fixes with null phone GPS speed during capture. The uploader converts stored speed to mph rounded to one decimal. The APK calls the same conversion in its upload path. | Use the nearest exact board speed within one second. Drop points without a fresh match. |
| How do we encode missing altitude or accuracy? | Passes Android location altitude and horizontal accuracy through in metres. The upload substitutes numeric zero for either missing value. | The fork stores missing altitude and accuracy as zero. Upload passes stored altitude through and substitutes 20 m for falsy accuracy, including zero. The APK uses the same upload fallback. | Follow Float Control and use zero on the wire when either value is absent. Preserve reported zero and negative values. |
| How do we handle route gaps and privacy trimming? | Sends one five-decimal polyline and one point list. Skips rows without coordinates and points inside the configured home radius. Remaining coordinates are adjacent in the polyline even across an omitted span. | Encodes the saved locations as one polyline and one point list. The upload code has no gap marker or home-radius filter. | Use one polyline over the included points, with their actual timestamps. Keep local gap markers intact and disclose the route submission in confirmation. |
| What distance and duration do we send? | Sends the logged ride distance in metres minus the previous sent distance on a subsequent upload. Uses whole elapsed seconds from the first included sample to the ride end. Formats ride and point times as UTC with second precision. | Sums distances between GPS points, rounds to 0.1 km, then converts to metres. Uses rounded whole seconds from session start to end and UTC timestamps with milliseconds. | Send logged board distance in metres, with start and end taken from the first and last included GPS observations. Send whole elapsed seconds and UTC timestamps with second precision. |
| Which rides qualify and how large can a submission be? | The inspected send action targets the current ride. No first-upload duration, distance, point-count minimum, or explicit request-size cap was found in the inspected builder. Its 100 m check applies to a ride with a saved Hermes ID. | Requires a completed session, at least three GPS points, at least 60 s, and at least 100 m by its rounded GPS calculation. Build 379 also excludes imported sessions. No explicit per-ride point or byte cap was found in the upload path. | Allow explicitly selected completed rides, including imports. Require three matched locations, 60 seconds between the first and last matched points, and 100 m of logged ride distance. Reject requests exceeding 2,000 points or 384 KiB. |
| Is a vehicle or visibility selection needed? | The inspected upload serializes `user_vehicle_id: null`. It sends no visibility field. | Omits the unset `user_vehicle_id` field and sends no visibility field. | Send a null vehicle ID and use Hermes defaults. Verify visibility and vehicle-free scoring with a test account. |
| What counts as a successful upload? | Requires a successful HTTP response with a parseable `ride.id`. Persists the ID in the local ride record and shows upload success. | Parses a response as JSON and checks HTTP success. Keeps a batch-level `lastSyncDate` after the sync finishes. The client does not retain an individual remote ride ID. | Save the per-ride receipt and show that Hermes accepted the ride. Add a link when an official route is confirmed. |
| What happens when a response is lost or a ride is sent again? | Reports a general failure when no ID comes back. After a confirmed upload it skips another send unless the ride has grown by more than 100 m, then attempts to post the additional portion. | A fetch, JSON, or HTTP failure stops the batch before its checkpoint advances. Later sync can revisit rides accepted earlier in that batch. | Persist uncertain outcomes and explain the uncertainty and prompt the rider to check Hermes before explicitly retrying. Treat explicit refusals as failed. Neither inspected path uses idempotency or reconciliation. |
| How are sign-in, account identity, and expiry handled? | Direct email/password sign-in. The response model has a token and optional user details. The client displays username, email, or typed email and clears local values on sign-out. | Browser callback returns the token, then `GET /users/id` supplies ID and username. Disconnect clears local state. | Use direct sign-in and require a stable rider ID. Return to sign-in when Hermes rejects the token. No token refresh or server-side revocation was found in either inspected flow. |

## Verification

Cover the observed auth and upload wire shape with a local Hermes test double. Use synthetic sessions for timestamp alignment, mph conversion, negative and zero altitude, missing values, gaps, request limits, and repeated or uncertain submissions. Run the affected shared frontend, backend, native bridge, and conformance checks. Verify credential entry and persistence on each supported host. With a partner-approved test account, verify one representative upload and its visibility and trail processing. [Project verification guide](../../../docs/development.md#verification)
